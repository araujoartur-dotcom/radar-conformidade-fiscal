## 🎯 A Causa Raiz Central: O Efeito Dominó do Header `x-empresa-ativa-id`

No commit de multi-tenant (`be6e490`), foi feita uma melhoria para que o frontend informasse em cada requisição qual empresa está ativa, adicionando este header HTTP:
```typescript
// src/hooks/useApi.ts
if (empresaAtiva?.id) {
  headers['x-empresa-ativa-id'] = empresaAtiva.id;
}
```

No entanto, no backend (`server/app.ts`), a configuração de CORS estava assim:
```typescript
// server/app.ts (Linha 106)
allowedHeaders: ['Content-Type', 'Authorization'],
```
**O header `x-empresa-ativa-id` NÃO foi incluído em `allowedHeaders`!**

### O que acontece no navegador do usuário:
1. **O Login funciona:** Quando você digita e-mail e senha, ainda não há empresa ativa no estado, logo o header não é enviado e o login tem sucesso (`200 OK`).
2. **Bloqueio total imediato:** No milissegundo em que o login conclui e o sistema define a empresa ativa, **todas as requisições seguintes do frontend** passam a injetar `x-empresa-ativa-id`.
3. Como o Netlify compila chamadas apontando para o Render (`https://radar-conformidade-fiscal.onrender.com`), o navegador do cliente dispara uma requisição de segurança chamada **CORS Preflight (`OPTIONS`)**.
4. O servidor responde: *"Eu só aceito Content-Type e Authorization"*.
5. O navegador então **bloqueia sumariamente todas as requisições subsequentes**. Nenhuma informação de KPI, DF-e, usuário ou tabela fiscal consegue chegar à tela.

Além disso, o frontend foi compilado com a URL absoluta do Render embutida no código, fazendo o navegador ignorar o proxy do `netlify.toml` e caindo de cabeça no bloqueio de CORS.

## 🛡️ Mecanismos de Proteção para Nunca Mais Acontecer

Para que seus clientes corporativos e você nunca mais enfrentem essa instabilidade, precisamos implementar **4 barreiras de proteção automatizadas**:

### 1. Blindagem de Comunicação via Same-Origin Proxy (Netlify -> Render)
O frontend **não deve chamar o Render diretamente com URL absoluta no navegador**. Ele deve chamar sempre a rota relativa `/api/*`.
* O Netlify recebe a chamada como se fosse dele mesmo (mesmo domínio `radarconformidade.netlify.app`), eliminando 100% das requisições Preflight de CORS.
* O Netlify encaminha a requisição pelo backend diretamente para o Render.
* **Resultado:** Impossível haver bloqueio de CORS no navegador dos clientes, mesmo que headers customizados sejam criados.

### 2. Liberação Completa de Headers no Backend Express
Em `server/app.ts`, configurar explicitamente:
```typescript
allowedHeaders: [
  'Content-Type',
  'Authorization',
  'x-empresa-ativa-id',
  'x-tenant-id',
  'x-requested-with'
],
```
Dessa forma, mesmo que uma chamada direta ocorra, o servidor aceita o header sem descartar a requisição.

### 3. "Smoke Test / Sanity Gate" Automatizado Pré-Deploy (CI/CD)
Criar um script de teste de sanidade (`scripts/verify-production-sanity.ts`) que roda automaticamente antes de qualquer deploy.
Esse script testa:
* Login do Admin Master;
* Troca de empresa ativa;
* Busca de KPIs globais e por empresa;
* Consulta de DF-e, usuários e tabelas fiscais;
* Verificação de CORS Preflight.
Se qualquer teste falhar, o build do deploy é **abortado antes de ir para os clientes**.

### 4. Notificação Transparente de Erro de Conexão no Frontend
Em vez de telas "em branco" ou valores "0" quando uma requisição falhar, o frontend exibirá um aviso claro com botão de reconectar:  
*"Não foi possível sincronizar com o servidor em nuvem (Render acordando ou falha de rede). [Tentar Novamente]"*.
